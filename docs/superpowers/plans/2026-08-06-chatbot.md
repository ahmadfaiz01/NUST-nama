# NUST Nama Chatbot — Implementation Plan (Plan B)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A chat feature where a signed-in NUST student asks a question and gets an
answer built from NUST's own documents, with a citation on every answer, plus live
answers about events already in the app's database.

**Architecture:** An agent loop written directly against Groq's OpenAI-compatible
API — no framework. The model is given five tools and decides which to call. Tool
calls run against the corpus Plan A produced and against the existing `events`
tables. The loop runs inside a Next.js route handler and streams to the client.

**Tech Stack:** Next.js 16 App Router, TypeScript, Groq (`openai/gpt-oss-120b`),
Supabase Postgres with `pgvector`, the existing `embed` edge function.

**Depends on Plan A.** `documents` and `sections` are populated and embedded, and
`search_sections()` works. Verified 2026-08-06.

## Global Constraints

- Source of truth: `docs/superpowers/specs/2026-08-06-rag-chatbot-design.md`.
- Signed-in NUST students only. Reuse the existing Supabase session; no new auth.
- **Every answer carries a citation**: document title, heading path, page range,
  publication date, and a link to NUST's original URL — never our storage copy.
- Question embeddings MUST come from the same `embed` edge function that embedded
  the sections. A different model returns confident nonsense with no error.
- **Provider chain, not a single provider.** Groq, a second Groq key, then Gemini,
  in `src/lib/chat/providers.ts`. All three expose an OpenAI-compatible API, so a
  fallback is a different base URL and model, not a different adapter. Fail over
  only on 429 / 402 / 5xx — a 400 means our own request is malformed and will fail
  identically everywhere, so retrying it burns every quota at once.
- Pin the provider for the duration of one tool loop. Switching mid-loop hands one
  model another model's tool calls; it mostly works but makes failures unreadable.
- Record which provider answered in `chat_messages`. Answer quality will differ
  between gpt-oss-120b and Gemini Flash, and you need to be able to tell.
- **The chain is for chat only.** Embeddings must never fall back. Sections were
  embedded with gte-small inside Supabase; a query embedded by any other model
  lands somewhere unrelated in vector space and search returns confident nonsense
  with no error. This is the single most dangerous thing to get wrong here.
- Even chained, free tiers run out. Show "busy, try again shortly" rather than an
  error when every provider is exhausted.
- Per-user quota only, ~30/day, enforced by one `count(*)`. The owner declined a
  global ceiling; Groq's own daily cap acts as one regardless.
- No LangChain. The agent loop is about 40 lines and must stay readable.
- Model id lives in one config constant so switching is a one-line change.

## File Structure

```
src/lib/chat/
  tools.ts        tool JSON schemas + their implementations
  agent.ts        the loop: call model, run tools, repeat, answer
  quota.ts        per-user daily limit
  cache.ts        answer cache keyed on the normalised question
src/app/api/ask/
  route.ts        POST, streams, enforces quota
src/app/ask/
  page.tsx        full chat page
src/components/chat/
  ChatPanel.tsx   the shared component — page and bubble both render this
  ChatBubble.tsx  floating launcher, renders ChatPanel compact
  Citation.tsx    one source, with the staleness warning
src/app/admin/documents/
  page.tsx        recently indexed feed, blacklist toggle
supabase/migrations/
  20260808_chat_tables.sql   chat_messages, answer_cache
```

`tools.ts` holds both the schemas and the implementations because they change
together — a tool whose schema and behaviour drift apart is the most common bug in
this kind of code.

## Task 1: Chat tables

**Files:**
- Create: `supabase/migrations/20260808_chat_tables.sql`

**Interfaces:**
- Produces: tables `chat_messages`, `answer_cache`

- [ ] **Step 1: Write the migration**

```sql
create table if not exists public.chat_messages (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null references public.profiles(id) on delete cascade,
  question   text not null,
  answer     text,
  sources    jsonb,
  tool_calls jsonb,
  created_at timestamptz not null default now()
);

create index if not exists chat_messages_user_day_idx
  on public.chat_messages (user_id, created_at desc);

alter table public.chat_messages enable row level security;

drop policy if exists "users read own chat" on public.chat_messages;
create policy "users read own chat" on public.chat_messages
  for select to authenticated using (user_id = auth.uid());

create table if not exists public.answer_cache (
  question_hash text primary key,
  answer        text not null,
  sources       jsonb not null,
  created_at    timestamptz not null default now()
);

create index if not exists answer_cache_created_idx
  on public.answer_cache (created_at);
```

Writes go through the service role in the route handler, so no insert policy is
needed — and not having one means a stolen anon key cannot forge chat history.

- [ ] **Step 2: Apply**

Paste into the Supabase SQL Editor. Do NOT use `supabase db push` — this repo's
migrations folder has colliding version prefixes and a cron migration containing
placeholder credentials that would overwrite live config.

- [ ] **Step 3: Verify**

```sql
select count(*) from chat_messages;
select count(*) from answer_cache;
```
Expected: `0` from both, no error.

- [ ] **Step 4: Commit**

```bash

git commit -m "feat(db): chat_messages and answer_cache"
```

## Task 2: The tools

**Files:**
- Create: `src/lib/chat/tools.ts`

**Interfaces:**
- Produces: `TOOL_SCHEMAS` (array of OpenAI-format tool definitions) and
  `runTool(name: string, args: any, userId: string): Promise<unknown>`

- [ ] **Step 1: Define the five tools**

```typescript
export const TOOL_SCHEMAS = [
  {
    type: "function",
    function: {
      name: "search_sections",
      description:
        "Search NUST's official documents for a topic. Use the vocabulary the " +
        "documents use, not the student's. A student asking 'how many classes " +
        "can I miss' should be searched as 'attendance requirement'.",
      parameters: {
        type: "object",
        properties: {
          query: { type: "string", description: "Search terms in document vocabulary" },
          doc_type: {
            type: "string",
            enum: ["policy", "fee", "scholarship", "prospectus", "form", "campus", "faq"],
            description: "Optional filter",
          },
        },
        required: ["query"],
      },
    },
  },
  {
    type: "function",
    function: {
      name: "read_section",
      description: "Read one section in full, by id, when a search snippet is not enough.",
      parameters: {
        type: "object",
        properties: { section_id: { type: "string" } },
        required: ["section_id"],
      },
    },
  },
  {
    type: "function",
    function: {
      name: "find_forms",
      description:
        "Find the form a student must fill in. Call this for any procedural " +
        "question - freezing a semester, migration, rechecking a paper.",
      parameters: {
        type: "object",
        properties: { topic: { type: "string" } },
        required: ["topic"],
      },
    },
  },
  {
    type: "function",
    function: {
      name: "search_events",
      description: "Find campus events happening soon. For questions about what is on.",
      parameters: {
        type: "object",
        properties: {
          query: { type: "string" },
          days_ahead: { type: "integer", description: "Default 14" },
        },
      },
    },
  },
  {
    type: "function",
    function: {
      name: "get_my_rsvps",
      description: "Events the student has RSVP'd to.",
      parameters: { type: "object", properties: {} },
    },
  },
] as const;
```

The `search_sections` description carries the vocabulary instruction deliberately.
Measured in Plan A: "how many classes can I miss" returns nothing useful, while
"attendance requirement" finds the rule. Bridging that gap is the model's job, and
this is where it is told so.

- [ ] **Step 2: Implement `runTool`**

Each implementation uses the Supabase service-role client.

- `search_sections` — embed the query via the `embed` edge function, then
  `rpc("search_sections", { query_text, query_embedding, match_count: 6, filter_doc_type })`.
  Return only `section_id`, `heading_path`, `content` truncated to 1200 chars,
  `url`, `title`, `page_start`, `page_end`, `published_at`. Never return the
  embedding.
- `read_section` — select the full row by id.
- `find_forms` — same as `search_sections` with `filter_doc_type: 'form'`.
- `search_events` — select from `events` where `status = 'approved'` and
  `start_time` between now and now + `days_ahead`, ordered by `start_time`.
- `get_my_rsvps` — join `rsvps` to `events` for `userId`.

`userId` comes from the session in the route handler and is NEVER taken from model
arguments. A model that could choose whose RSVPs to read would be an access
control hole.

- [ ] **Step 3: Verify each tool standalone**

Write `src/lib/chat/tools.test.ts` or a scratch script calling each with a fixed
input, and print the results. Confirm `search_sections("attendance requirement")`
returns the section whose heading ends `f. Attendance`.

- [ ] **Step 4: Commit**

```bash
git add src/lib/chat/tools.ts
git commit -m "feat(chat): agent tools over documents and live events"
```

## Task 3: The agent loop

**Files:**
- Create: `src/lib/chat/agent.ts`

**Interfaces:**
- Consumes: `TOOL_SCHEMAS`, `runTool`
- Produces: `askAgent(question: string, userId: string): AsyncGenerator<AgentEvent>`
  where `AgentEvent` is `{type:'tool', name:string} | {type:'token', text:string} | {type:'done', sources:Source[]}`

- [ ] **Step 1: Write the system prompt**

It must instruct the model to:
- answer only from tool results, never from its own knowledge of universities
- say plainly when the documents do not contain the answer
- cite the heading path and page of every section used
- call `find_forms` for procedural questions, alongside the policy lookup
- warn when a fee or deadline answer comes from a document older than the current
  academic year
- prefer the newest document when two disagree
- reply in the language the student used

- [ ] **Step 2: Write the loop**

```typescript
const messages = [systemPrompt, userQuestion];
for (let turn = 0; turn < MAX_TURNS; turn++) {
  const response = await callGroq(messages, TOOL_SCHEMAS);
  if (!response.tool_calls) return response.content;   // model answered
  for (const call of response.tool_calls) {
    const result = await runTool(call.function.name, JSON.parse(call.function.arguments), userId);
    messages.push({ role: "tool", tool_call_id: call.id, content: JSON.stringify(result) });
  }
}
```

`MAX_TURNS = 4`. Without a cap a confused model calls tools forever and each turn
costs tokens against a 200,000/day budget.

- [ ] **Step 3: Handle 429**

Groq returns `retry-after`. Surface a "busy, try again shortly" event rather than
throwing — the free tier will hit this.

- [ ] **Step 4: Verify from the command line before any UI exists**

```bash
npx tsx scripts/ask.ts "how many classes can I miss"
npx tsx scripts/ask.ts "how do I freeze a semester"
npx tsx scripts/ask.ts "what events are on this week"
```

The first is the decisive test. Plan A proved raw search fails on that phrasing.
If the agent reformulates to "attendance requirement" and returns the 75% rule,
the loop is doing its job. **If it does not, do not proceed** — the whole design
rests on the model bridging that vocabulary gap.

- [ ] **Step 5: Commit**

## Task 4: Quota and cache

**Files:**
- Create: `src/lib/chat/quota.ts`, `src/lib/chat/cache.ts`

**Interfaces:**
- Produces: `checkQuota(userId): Promise<boolean>`,
  `getCached(question): Promise<CachedAnswer|null>`,
  `putCached(question, answer, sources): Promise<void>`

- [ ] **Step 1: Quota**

One count against `chat_messages` for today. Over 30, return false.

- [ ] **Step 2: Cache**

Key is a sha256 of the question lowercased, trimmed, with runs of whitespace
collapsed. Ignore entries older than 30 days.

- [ ] **Step 3: Invalidation**

When ingestion updates or blacklists a section, delete every `answer_cache` row
whose `sources` contains that section id. Without this the cache serves last
semester's fee deadline forever, defeating the entire staleness design. Add this
to `ingest/pipeline.py` where sections are replaced.

- [ ] **Step 4: Verify**

Ask the same question twice; the second must return from cache and make no Groq
call. Then blacklist a source document and confirm the cached answer disappears.

- [ ] **Step 5: Commit**

## Task 5: The API route

**Files:**
- Create: `src/app/api/ask/route.ts`

- [ ] **Step 1: Write it**

Order matters: session → quota → cache → agent.

1. Get the user from the Supabase server client. No session, 401.
2. `checkQuota`. Over, 429 with a friendly message.
3. `getCached`. Hit, stream it straight back.
4. Run `askAgent`, streaming events as server-sent events.
5. Write the row to `chat_messages` and `putCached` when finished.

- [ ] **Step 2: Verify**

`curl` it with a real session cookie. Confirm 401 without one, and that 31
consecutive questions produce a 429.

- [ ] **Step 3: Commit**

## Definition of done

- [ ] "how many classes can I miss" returns the 75% attendance rule with a citation
- [ ] "how do I freeze a semester" returns the policy AND the form's download link
- [ ] "what's on this week" returns real rows from `events`
- [ ] A question with no answer in the corpus gets an honest "I don't know"
- [ ] Every answer shows document, heading path, page and date
- [ ] 31st question in a day returns a friendly quota message
- [ ] Repeat questions come from cache without a Groq call
- [ ] Blacklisting a document removes it from answers and clears cached answers
- [ ] Works at 375px wide

## Deliberately not in this plan

- No follow-up memory. Each question stands alone. Cheap to add; it complicates
  retrieval, so it waits until people ask for it.
- No streaming of tool results, only status labels.
- No answer feedback (thumbs up/down). Worth adding once real questions arrive —
  `chat_messages` already stores everything needed.
